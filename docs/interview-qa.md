### Q16: 你们的 Agent 是真正的 AI Agent 吗？

**坦诚回答：不是。**

当前 6 个 Agent 是"实现了统一接口的业务逻辑模块"，内部没有 LLM 调用、没有 ReAct 推理循环、没有工具调用。叫 Agent 是因为：
- 接口按 Agent 模式设计，后续接入 LLM 只需替换 process() 实现
- 全链路追溯、置信度、A2AMessage 协议等架构是为真实 AI Agent 准备的

**切换路径**：
```
当前: process() { 硬编码逻辑 → 返回结果 }
Phase1: process() { 调用 OCR/LLM API → 返回结果 }
Phase2: process() { ReAct 循环 → 自主调工具 → 返回结果 }
```

### Q17: 系统有哪些关键设计决策？

| 决策 | 选择 | 理由 |
|------|------|------|
| 为什么自研编排器而不是 LangGraph？ | 自研（MVP）→ LangGraph（生产） | MVP 快速验证，生产需要条件路由 |
| 为什么用 SQLite？ | SQLite（开发）→ PostgreSQL（生产） | 零配置开发，ORM 已解耦 |
| 为什么 Agent 全部模拟？ | 模拟 MVP → 真实 LLM Phase1 | 先验证链路完整性 |
| 为什么强制人工授权？ | 保险监管合规 | AI 只出建议，人工最终确认 |
| 为什么规则引擎前置？ | 省 Token 费用 | 50% 案件不走 LLM |

### Q18: 系统目前有哪些致命短板？

1. **零真实 AI 能力** — OCR/LLM/RAG 全是模拟，无法处理真实理赔
2. **SQLite 并发限制** — 多用户同时操作会锁库
3. **Payload 膨胀** — 虽然已优化，但架构层面应改用 Trace Store
4. **无监控告警** — 无法感知系统运行状态和异常
5. **无灾备** — 数据库无备份，文件存储无冗余
